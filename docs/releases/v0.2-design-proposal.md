# ConfigGuard v0.2 Design Proposal

**Version:** 0.2-draft
**Date:** 2026-05-29
**Status:** Planning

---

## Problem Statement

v0.1 has stable architecture but suffers from **rule duplication / abstraction gap**:

- Multiple atomic rules detect the same config observation independently
- Example: "transport input telnet" triggers both CISCO-MGMT-001 and CISCO-MGMT-003
- Rules directly match against raw config text, no canonical input space

---

## Core Upgrade: Signal Layer

### What is a Signal?

A **Signal** is a **canonical security observation** — a normalized representation of a security-relevant configuration fact.

```json
{
  "type": "vty_transport_input",
  "value": "telnet",
  "block": {
    "type": "line",
    "name": "vty 0 4"
  },
  "raw": "transport input telnet ssh"
}
```

### Signal Layer Benefits

| Benefit | Description |
|---------|-------------|
| Deduplication | Multiple rules subscribe to same signal, find duplicate eliminated |
| Normalization | Vendor-specific config → canonical security model |
| Extensibility | Adding new parsers (NX-OS, Juniper) only needs signal extraction |
| Reasoning | Rules operate on semantic model, not raw text |

---

## v0.2 Architecture

```
Config File (any vendor)
    ↓
Vendor-specific Parser
    ↓
Signals (canonical observations)
    ↓
Rule Engine (semantic rules)
    ↓
Findings JSON
    ↓
Output Layer
```

### Comparison

| Layer | v0.1 | v0.2 |
|-------|------|------|
| Input | config | config |
| Middle | rules only | signals + rules |
| Logic | regex-based | semantic-based |
| Duplication | possible | eliminated |
| Extensibility | medium | high |

## Rule Hierarchy

v0.2 introduces rule types:

### Atomic Rules (leaf)
Single signal evaluation:
```yaml
id: CISCO-MGMT-001
type: atomic
signal: mgmt_transport
condition:
  signal.value: contains(telnet)
finding: FAIL
```

### Composite Rules (derived)
Multiple signals or atomic rules:
```yaml
id: CISCO-MGMT-003
type: composite
depends_on:
  - CISCO-MGMT-001
condition: dependent findings >= 1
finding: derived
```

### Absent Rules
Signal NOT present when required:
```yaml
id: CISCO-AUTH-001
type: absent
signal: aaa_enabled
condition:
  signal.value: disabled
finding: FAIL
```

## Deduplication Model

Signal Layer deduplication happens at signal extraction:

```python
class SignalExtractor:
    def extract(self, config_ir) -> list[Signal]:
        signals = []
        seen = set()

        for block in config_ir.blocks:
            for cmd in block.commands:
                signal = self._normalize(block, cmd)
                sig_key = (signal.type, signal.value)
                if sig_key not in seen:
                    seen.add(sig_key)
                    signals.append(signal)

        return signals
```

Then rules operate on canonical signals — no duplicate findings.

## Migration Path

### v0.1 → v0.2 Compatibility

v0.2 must be **backward compatible** with v0.1:

1. YAML rules continue to work (v0.1 atomic rules become v0.2 atomic signals)
2. CLI interface unchanged
3. Output schema unchanged
4. Gradual migration: signals added incrementally

### Migration Strategy

```
Phase 1: Add Signal Layer (behind flag)
  configguard audit config.txt --signal-layer

Phase 2: Migrate rules to signals
  Each v0.1 rule → signal + atomic rule

Phase 3: Remove legacy mode
  v1.0: signal layer only
```

## Summary

**v0.2 Goal:** Transform ConfigGuard from "rule engine" to "normalized security reasoning system"

**Key changes:**
1. Add Signal Layer between parser and rule engine
2. Introduce rule hierarchy (atomic vs composite)
3. Eliminate duplicate findings
4. Enable multi-vendor extensibility

**v0.2 remains deterministic** — signals are derived, not AI-inferred.
