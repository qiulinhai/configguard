## 0. Validation Philosophy

| Approach | Risk |
|----------|------|
| Continue engineering then validate | Build something nobody wants |

### Core Question

> "Will a security engineer choose ConfigGuard over their current workflow?"

**Not asking:**
- Is the architecture correct?
- Is the IR model perfect?
- Are there enough adapters?

- Does the output make sense?
- Is the trust threshold met?

## 1. Test Hypotheses

### H1: Output Understandability
**Hypothesis**: Security engineers will understand CLI output without training.

**Test**: Give them `diff` output, ask:
- "What happened in this config change?"
- "What is the risk?"
- "What should you do?"

**Success criteria**: 80% can answer all 3 correctly without hints.

### H2: Actionability
**Hypothesis**: Engineers will act on `explain` output to fix issues.

**Test**: Give them a finding + explain output, ask:
- "Would you apply these fix commands?"
- "Would you need to modify them?"

**Success criteria**: 70% say "yes, I would apply or modify".

### H3: Workflow Integration
**Hypothesis**: Engineers will integrate ConfigGuard into CI/CD pipeline.

**Test**: Show them CI mode + exit codes, ask:
- "Would this fit in your deployment workflow?"
- "What would prevent adoption?"

**Success criteria**: 60% say "yes, with minor adjustments".

### H4: Competitive Differentiation
**Hypothesis**: ConfigGuard is preferred over manual audit / scripts.

**Test**: Compare ConfigGuard output vs. current method, ask:
- "Which would you use daily?"

**Success criteria**: >50% prefer ConfigGuard over current method.

### 3.2 Test Materials

#### Material A: `diff` Output (for H1, H4)

```bash
# configguard diff old.cfg new.cfg --ci
❗ SECURITY DRIFT DETECTED — Attack surface +37%

[CRITICAL] SNMP v2c public community exposed
  - Added in new.cfg line 42
  - Network exposure: internet-facing mgmt plane
  - Fix: Change community string

[WARNING] Telnet enabled alongside SSH
  - Modified in new.cfg line 55
  - Risk: Dual access method = higher exposure
  - Fix: Disable telnet, use SSH only

📊 Risk Delta: +37 → +74 (HIGH)
📋 Run `configguard explain abc123` for details
```

#### Material B: `explain` Output (for H2)

```bash
# configguard explain abc123 --finding CISCO-SNMP-001

🔍 FINDING: SNMP v2c Public Community

📖 What This Means:
  Your device has SNMP version 2c enabled with the default "public" 
  community string. This allows anyone with network access to read 
  your entire running configuration and map your internal network.

🗺️ Attack Path:
  Internet → SNMP (port 161) → Device Config → Network Map

🔧 Recommended Fix:
  1. Change community string:
     snmp-server community <random> RO
  
  2. Restrict SNMP access:
     snmp-server community <secret> RO 10.0.0.0/8

  3. Consider migrating to SNMPv3 with authPriv
```

#### Material C: CI/CD Integration (for H3)

```bash
# .github/workflows/config-audit.yml
name: Config Security Audit
on: [pull_request]

jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: Run ConfigGuard diff
        run: |
          git diff ${{ github.event.pull_request.base.sha }}
                  ${{ github.event.pull_request.head.sha }}
                  -- configs/ > changes.diff
          
          configguard diff \
            --base ${{ github.event.pull_request.base.sha }} \
            --head ${{ github.event.pull_request.head.sha }} \
            --ci --policy cis --fail-on HIGH

      - name: PR Comment
        if: failure()
        uses: configguard/pr-comment@v1
```

**Exit Codes:**
- 0: No drift (PASS)
- 1: LOW/MEDIUM only (WARN)
- 2: HIGH/CRITICAL (FAIL)

### 3.3 Question Scripts

#### H1: Output Understandability Questions

```
[Show Material A]

Q1: "What do you understand this output to say?"
Q2: "What changed in this config?"
Q3: "How risky is this change on a scale of 1-10?"
Q4: "What would you do next?"
Q5: "Is there anything confusing about this output?"
```

**Scoring:**
- Q1-4: Correct answer = 1 point each
- Q5: No confusion = 0, Confusion noted = -1
- Total: 4/4 = full understanding, 2/4 = partial, <2 = failed

#### H2: Actionability Questions

```
[Show Material B]

Q1: "Would you apply these fix commands?"
Q2: "What would you need to change before applying?"
Q3: "How long would this take to implement?"
Q4: "Do you trust these fix recommendations?"
Q5: "What's missing from this fix recommendation?"
```

**Scoring:**
- Q1: "Yes" = 2, "Modified" = 1, "No" = 0
- Q4: "Yes" = 2, "Maybe" = 1, "No" = 0
- Total: 4/4 = actionable, 2/4 = needs work, <2 = not actionable

#### H3: Workflow Integration Questions

```
[Show Material C]

Q1: "Would this fit in your CI/CD pipeline?"
Q2: "What would you need to change?"
Q3: "What would prevent adoption?"
Q4: "How often would you run this?"
Q5: "Would you pay for this feature?"
```

**Scoring:**
- Q1: "Yes, as-is" = 2, "With changes" = 1, "No" = 0
- Q3: Barriers listed = 0, No barriers = 1
- Total: 3/4 = integrable, 2/4 = needs work, <2 = integration unlikely

#### H4: Competitive Differentiation Questions

```
Q1: "What do you currently do for config security review?"
Q2: "How much time does that take per device/week?"
Q3: "What are the main pain points?"
Q4: "Compared to your current method, would you use ConfigGuard?"
Q5: "What would need to be true for you to switch?"
```

**Scoring:**
- Q4: "ConfigGuard" = 2, "Depends" = 1, "Current" = 0
- Total: 2/2 = strong preference, 1/2 = neutral, 0/2 = stick with current

### 3.4 Success Metrics

| Hypothesis | Success Threshold | Measurement |
|------------|-------------------|-------------|
| H1: Understandability | 80% pass rate (4/4) | Test session scoring |

```
  → Do NOT release v1.0

If 3/4 hypotheses pass:
  → Release v1.0 with noted improvements

If 4/4 hypotheses pass:
  → Ready for v1.0 release
  → Consider faster timeline
```

## 6. Adoption Signals

### 6.1 Early Adoption Indicators

These signals predict successful adoption if met:

```
Signal 1: time-to-first-use < 5 min
  → User ran first command without asking for help

Signal 2: explain command used voluntarily
  → User proactively explored deeper output

Signal 3: "This makes sense" unprompted
  → User expressed trust without prompting

Signal 4: Asked about CI/CD integration
  → User saw workflow fit immediately

Signal 5: Offered to show colleagues
  → User wants to share with team
```

### 6.2 Warning Signals

These indicate risk of low adoption:

```
Warning 1: Required explanation to understand output
Warning 2: "We already have something like this"
Warning 3: "I'd need to check with my team"
Warning 4: Config change not worth action
Warning 5: Asked about pricing before trying
```

## 7. Go/No-Go Decision Framework

### 7.1 Go Decision

```
✅ GO if:
  - 3/4 hypotheses pass
  - H1 (Understandability) passes at 80%+
  - No >1 "fundamental confusion" patterns
  - Early adoption signals present
```

### 7.2 No-Go Decision

```
❌ NO-GO if:
  - < 3/4 hypotheses pass
  - H1 (Understandability) fails
  - Multiple "fundamental confusion" patterns
  - User trust not established
  - Users prefer current method over ConfigGuard
```

### 7.3 Conditional Go

```
⚠️ CONDITIONAL GO if:
  - 3/4 hypotheses pass
  - BUT H2 (Actionability) borderline
  → Release v1.0 with explicit fix roadmap
  → Address actionability in v1.1
```
