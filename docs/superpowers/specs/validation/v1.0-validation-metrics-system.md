# ConfigGuard v1.0 — Validation Metrics System

**Status**: Design Draft
**Version**: v1.0
**Date**: 2026-05-30
**Purpose**: Define how to extract maximum signal from 6-10 user validation sessions

---

## 0. Design Philosophy

### Core Question

> "How do we extract 10x information from each user session without optimizing for metrics instead of users?"

### What This System Is NOT

This system does NOT define:
- **Production scoring weights** — Will be recalibrated after first user batch
- **Final product risk formula** — Based on real trust behavior, not assumptions
- **CI/CD gating thresholds** — Learned from integration feedback, not guessed
- **Go/No-Go decision criteria** — Evolves with user data quality

**Why:** Premature instrumentation lock-in causes Goodhart's Law. When we measure a system, the system optimizes for the measure, not the reality.

### Metric Stability Policy

All metrics are considered:
- **Hypothesis-driven** (not truth) — Each metric tests a specific hypothesis
- **Versioned** (v1.0 → v1.1 → v2.0) — Recalibrated after each user batch (n ≥ 6)
- **Recalibrated after each user batch** — First batch identifies what actually matters
- **Behavior-not-score-driven** — We optimize for real behavior change, not score improvement

## 2. Trust Calibration Tests

### TCT-1: Trust Calibration Test

**Hypothesis:** ConfigGuard earns trust vs. manual methods

```
[Show Material A: ConfigGuard diff output]
[Show baseline: Manual SSH + show commands interpretation]

Q1: "Which would you trust for a real security decision?"
A: ConfigGuard / Baseline / Depends

Q2: "Why?"
[Record verbatim]
```

**Scoring:**
- ConfigGuard = +2 (trust signal)
- Baseline = 0 (status quo bias)
- Depends = +1 (conditional)

### TCT-2: Override Test

**Hypothesis:** Users with strong opinions will override ConfigGuard (adoption risk)

```
[Show Material A with ConfigGuard saying: Risk Delta +37 (MEDIUM)]

Q1: "What is YOUR personal risk assessment? Rate 1-10"
[Record rating]

Q2: "ConfigGuard says MEDIUM. You rated [X]. What would you do?"
A: Follow ConfigGuard / Override / Escalate

[If Override]: "What would need to be true for you to follow ConfigGuard?"
[Record verbatim]
```

**Scoring:**
- Follows ConfigGuard = +2 (trust signal)
- Overrides = 0 (adoption risk)
- Escalates = +1 (needs more info, not rejection)

**Override Direction Tracking:**
- User rates HIGHER than ConfigGuard = "LOW→HIGH override" (more cautious)
- User rates LOWER than ConfigGuard = "HIGH→LOW override" (more confident/risky)

### TCT-3: Fix Execution Test

**Hypothesis:** Fix recommendations are executable without modification

```
[Show Material B: explain output with fix commands]

Q1: "Can you apply these fix commands to your environment?"
A: Yes / With changes / No

Q2: "What would you need to change?"
[Record verbatim]

Q3: "How long would this take you?"
< 15 min = +2
15-30 min = +1
> 30 min = 0
```

## 3. Metrics Aggregation

### Per-Session Score Summary

```python
@dataclass
class SessionScore:
    h1_score: int        # /4
    h2_score: int        # /4
    h3_score: int        # /4
    h4_score: int        # /2
    tct_score: int       # /6
    adoption_signals: int  # /5
    warning_signals: int  # /5
```

### Per-Hypothesis Aggregation

```python
def aggregate_h1(sessions: list[Session]) -> float:
    """H1 pass rate: understandability"""
    passed = sum(1 for s in sessions if s.h1_score >= 4)
    return passed / len(sessions)

def aggregate_h2(sessions: list[Session]) -> float:
    """H2 actionable rate"""
    passed = sum(1 for s in sessions if s.h2_score >= 4)
    return passed / len(sessions)

def aggregate_h3(sessions: list[Session]) -> float:
    """H3 integrable rate"""
    passed = sum(1 for s in sessions if s.h3_score >= 3)
    return passed / len(sessions)

def aggregate_h4(sessions: list[Session]) -> float:
    """H4 preference rate"""
    passed = sum(1 for s in sessions if s.h4_score >= 1)
    return passed / len(sessions)
```

### Trust Calibration Score

```python
def compute_trust_calibration(sessions: list[Session]) -> float:
    """ConfigGuard trust vs baseline trust, normalized 0-1"""
    total_trust = sum(s.tct_score for s in sessions)
    max_trust = len(sessions) * 6  # max 6 per session
    return total_trust / max_trust
```

### Adoption Probability Model (PROVISIONAL — v1.1)

**NOTE: This formula is assumed, not validated. Will be recalibrated after first batch.**

```python
def compute_adoption_probability(sessions: list[Session]) -> float:
    """
    provisional_adoption = adoption_rate * (1 - warning_rate * 0.5)
    
    WARNING: This is a hypothesis, not a measurement.
    Goodhart's Law applies: once we optimize for this, it stops predicting adoption.
    """
    adoption_rate = sum(s.adoption_signals for s in sessions) / (len(sessions) * 5)
    warning_rate = sum(s.warning_signals for s in sessions) / (len(sessions) * 5)
    
    provisional_adoption = adoption_rate * (1 - warning_rate * 0.5)
    
    return provisional_adoption
```

### Override Resistance (PROVISIONAL — v1.1)

**NOTE: This metric is leading indicator, not validated predictor.**

```python
def compute_override_resistance(sessions: list[Session]) -> float:
    """
    Returns: fraction of sessions where user overrode ConfigGuard assessment.
    Higher = more adoption resistance (concerning).
    Zero = all users followed ConfigGuard (ideal).
    
    NOTE: Override behavior is complex:
    - Override may mean user is engaged, not that they distrust
    - Low override may mean user is passive, not that they trust
    """
    override_count = sum(
        1 for s in sessions 
        if s.override_behavior in ["HIGH→LOW", "LOW→HIGH"]
    )
    return override_count / len(sessions)
```

## 4. Go/No-Go Decision Framework

**NOTE: Decision thresholds are provisional. Will be recalibrated after first user batch.**

### Hypothesis Pass Thresholds

| Hypothesis | Success Threshold | Notes |
|------------|------------------|-------|
| H1: Understandability | ≥80% pass (4/4) | CRITICAL — foundation |
| H2: Actionability | ≥70% actionable (4/4) | Builds on H1 |
| H3: Integration | ≥60% integrable (3/4) | CI/CD context |
| H4: Differentiation | ≥50% prefer | vs current method |

### Decision Matrix

```
                    H1 Pass ≥80%?
├─ NO  → NO-GO (output not understood, nothing else matters)
└─ YES → Continue

                         H1 Pass ≥80%?
                         ├─ NO  → NO-GO
                         └─ YES → Continue
```

**Combined threshold:** 3/4 hypotheses must pass AND H1 must pass at ≥80%

### Decision Categories

| Verdict | Conditions | Action |
|---------|------------|--------|
| **GO** | 3/4 pass + H1 ≥80% + adoption_prob > 0.5 | Proceed to v1.0 release |
| **CONDITIONAL** | 3/4 pass + H1 ≥80% + adoption_prob ≤ 0.5 | Release with noted adoption risks |
| **NO-GO** | <3/4 pass OR H1 <80% | Return to UX design |

### What Triggers Conditional GO

```
CONDITIONAL GO if:
  - 3/4 hypotheses pass
  - H1 (Understandability) passes at 80%+
  - BUT adoption_probability < 0.5
  - OR override_resistance > 0.4

→ Release v1.0 with explicit improvement roadmap
→ Address adoption barriers in v1.1
```

## 5. Per-User-Type Aggregation

**Purpose:** Identify which user types are adoption risks, which are amplifiers.

```python
USER_TYPES = [
    "Network Security Analyst",
    "DevOps/Platform Eng",
    "Security Auditor", 
    "Platform Lead",
]

def aggregate_by_user_type(sessions: list[Session]) -> dict:
    """
    Returns dict of ValidationResult per user type.
    Use to identify:
    - Which types adopt readily (amplifiers)
    - Which types need more evidence (risks)
    - Which types are decision blockers (power users)
    """
    results = {}
    for utype in USER_TYPES:
        type_sessions = [s for s in sessions if s.user_type == utype]
        if type_sessions:
            results[utype] = compute_verdict(type_sessions)
    return results
```

**What to look for:**
- Network Security Analyst passes H1+H2 but fails H3 → CI/CD integration needs work
- DevOps passes H3 but fails H1 → Output format too verbose for their workflow
- Security Auditor fails H4 → Need compliance-specific framing

## 6. Stability and Recalibration Policy

### Version History

| Version | Changes | Trigger |
|---------|---------|---------|
| v1.0 | Initial design (all provisional) | First spec |
| v1.1 | Recalibrated after first batch (n≥6) | First user batch |
| v2.0 | Second recalibration | Second user batch + production data |

### Recalibration Triggers

After each user batch (n ≥ 6), evaluate:
1. **Metric drift** — Are scores clustering differently than expected?
2. **Missing signals** — What did users do that we didn't measure?
3. **Correlations** — Which signals predict actual adoption?
4. **Override patterns** — Is override behavior consistent?

### Metrics to Watch (Don't Optimize)

These are **observational only**:
- `adoption_5_shares_colleagues` — May underestimate silent adoption
- `warning_4_config_not_worth_action` — May not predict real remediation behavior
- `tct_override_behavior` — May not correlate with long-term trust

## 7. What to Learn from First Batch (n=6-10)

### Questions to Answer

1. **Which hypothesis fails first?** (H1 usually)
2. **Is TCT-2 override behavior correlated with H4 preference?**
3. **Do adoption signals cluster in specific user types?**
4. **What's the average time-to-first-understanding?**
5. **Which fix commands are modified vs applied directly?**

### What to NOT Conclude

```
NOT valid conclusions from first batch:
- "adoption_probability = 0.6" — Too few users to validate model
- "override_resistance predicts churn" — No longitudinal data
- "H3 integrable → will integrate" — Stated intent ≠ actual behavior
- "Network analysts prefer ConfigGuard over DevOps" — n too small for type comparison
```

### Valid Conclusions from First Batch

```
Valid conclusions from first batch:
- Which hypothesis passes threshold
- Which user type needs most work
- What content is confusing (verbatim quotes)
- What adoption barriers exist (verbatim quotes)
- Whether test materials match real workflows
```

## 8. Session Execution Guide

### Before Sessions

**Do:**
- Read protocol section 3.3 (Question Scripts)
- Prepare materials A, B, C in printed/display format
- Have session tracker open in spreadsheet
- Record consent for video/audio if using

**Don't:**
- Coach users toward specific answers
- Explain what we're testing before they respond
- Rush the "Why?" questions — these are the real signal

### During Sessions

**TCT-2 Override Test — Critical Timing:**
- Ask personal risk rating BEFORE showing them ConfigGuard's rating
- If you show them ConfigGuard's rating first, you've contaminated the test

**Adoption Signals — Watch for these unprompted:**
- User asks about CI/CD without prompting
- User volunteers "I would use this"
- User shows colleagues without being asked
- User takes notes during the session

**Warning Signals — Don't Over-index:**
- "I would need to check with my team" — May mean organizational, not product
- "We already have something like this" — May mean differentiation gap OR feature gap
- Asked about pricing — May mean they're already evaluating ROI

### After Sessions

1. **Within 1 hour:** Complete session tracker while memory fresh
2. **Within 24 hours:** Note verbatim quotes that aren't in tracker
3. **Within 48 hours:** Flag concerning patterns to rest of team
4. **Weekly:** Aggregate batch results, update this spec

## 9. Summary

### The One Question This Metrics System Answers

> "Will a security engineer trust ConfigGuard over their current workflow?"

### How It Answers It

| Metric | What It Measures | What It Doesn't |
|--------|----------------|-----------------|
| H1 pass rate | Can they understand output? | Do they trust it? |
| H2 actionable rate | Will they act on it? | Will they actually fix? |
| H3 integrable rate | Does it fit CI/CD? | Will they integrate? |
| H4 preference rate | Do they prefer it? | Will they switch? |
| TCT trust score | Do they trust vs baseline? | Is trust durable? |
| Override resistance | Will they second-guess? | Will they abandon? |
| Adoption signals | Early engagement signs | Actual retention |

### Critical Insight

**We are building a measurement system for a system that does not yet have real-world calibration.**

The correct response is:
1. Freeze measurement design in spec
2. Use real users to break it
3. Recalibrate after first batch
4. Don't optimize for metrics — optimize for user behavior

## 10. Open Questions for First Batch

1. **Does TCT-2 override behavior predict H4 preference?**
   - If yes: Use override test as early warning
   - If no: Rethink override as adoption signal

2. **Do adoption signals correlate with actual CI/CD integration?**
   - If yes: Weight adoption signals more heavily
   - If no: Add longitudinal tracking for v1.1

3. **Is H1 threshold (4/4) too strict or too lenient?**
   - If many users score 3/4: Lower to 3/4 = pass
   - If many users score 2/4 with "understood but confused": H1 needs redesign

4. **Do verbatim quotes cluster by user type?**
   - If yes: Build type-specific messaging for v1.1
   - If no: Generic messaging is sufficient
