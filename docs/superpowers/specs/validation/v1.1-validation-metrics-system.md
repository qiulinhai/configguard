**Status**: Design Draft

## 0. Design Philosophy

### What This System Is NOT

This system does NOT define:
- **Production scoring weights** — Will be recalibrated after first user batch
- **Final product risk formula** — Based on real trust behavior, not assumptions
- **CI/CD gating thresholds** — Learned from integration feedback, not guessed
- **Go/No-Go decision criteria** — Evolves with user data quality

### Metric Stability Policy

All metrics are considered:
- **Hypothesis-driven** (not truth) — Each metric tests a specific hypothesis
- **Versioned** (v1.0 → v1.1 → v2.0) — Recalibrated after each user batch (n ≥ 6)
- **Recalibrated after each user batch** — First batch identifies what actually matters
- **Behavior-not-score-driven** — We optimize for real behavior change, not score improvement

## 2. Aggregation Functions (v1.1)

### H1 Aggregation

```python
def aggregate_h1(sessions: list[SessionScore]) -> dict:
    """
    H1 v1.1 reports:
    - h1_pass_rate: traditional 4/4 comprehension
    - h1x_pass_rate: unmet questions <= 1
    - h1_skeptic_rate: questions that are methodology concerns
    """
    passed_4_4 = sum(1 for s in sessions if s.h1_score >= 4) / len(sessions)
    passed_h1x = sum(1 for s in sessions if s.h1x_unmet_questions <= 1) / len(sessions)

    # Track skeptic questions separately
    skeptic_questions = [
        q for s in sessions for q in s.verbatim_skeptic_questions
    ]

    return {
        "h1_pass_rate": passed_4_4,
        "h1x_pass_rate": passed_h1x,
        "skeptic_question_count": len(skeptic_questions),
        "skeptic_questions": skeptic_questions,  # verbatim for analysis
    }
```

### TCT-2 Override Aggregation (4 States)

```python
def aggregate_override(sessions: list[SessionScore]) -> dict:
    """
    Override behavior now has 4 states:
    - FOLLOW: trusts ConfigGuard
    - OVERRIDE: has stronger opinion
    - ESCALATE: needs more info
    - DEFER: product dependency gates decision
    """
    counts = {
        "FOLLOW": 0,
        "OVERRIDE": 0,
        "ESCALATE": 0,
        "DEFER": 0,
    }
    for s in sessions:
        counts[s.tct_override_behavior] += 1

    total = len(sessions)
    return {
        f"{k}_rate": v / total for k, v in counts.items()
    }
```

### DEFER Analysis (Critical New Metric)

```python
def analyze_defer_conditions(sessions: list[SessionScore]) -> dict:
    """
    DEFER is not adoption failure — it's product dependency signal.

    Classify DEFER conditions:
    - INTEGRATION_GAP: "need to see it work with X"
    - FEATURE_GAP: "would adopt if they had Y"
    - EVIDENCE_GAP: "need to see it work for 6 months"
    - TEAM_GATE: "need to get team buy-in"
    """
    defer_conditions = [
        cond for s in sessions
        if s.tct_override_behavior == "DEFER"
        for cond in s.verbatim_defer_conditions
    ]

    # Classify
    integration_gap = [c for c in defer_conditions if "integrat" in c.lower()]
    feature_gap = [c for c in defer_conditions if any(
        f in c.lower() for f in ["feature", "would if", "if they had"]
    )]
    evidence_gap = [c for c in defer_conditions if any(
        e in c.lower() for e in ["prove", "6 months", "first", "see it work"]
    )]
    team_gate = [c for c in defer_conditions if "team" in c.lower() or "buy-in" in c.lower()]

    return {
        "defer_rate": sum(1 for s in sessions if s.tct_override_behavior == "DEFER") / total,
        "defer_conditions": defer_conditions,
        "by_category": {
            "integration_gap": integration_gap,
            "feature_gap": feature_gap,
            "evidence_gap": evidence_gap,
            "team_gate": team_gate,
        },
        "top_blocker": _most_common_category(defer_conditions),
    }
```

### CI/CD Intent Strength Aggregation

```python
def aggregate_cicd_intent(sessions: list[SessionScore]) -> dict:
    """
    CI/CD question is NOT automatically an adoption signal.
    Strength matters:

    weak: "do you have github action?" — just curious
    medium: "how does it integrate?" — considering
    strong: "how would i block PR on HIGH?" — concrete use case
    """
    weak = sum(1 for s in sessions if s.adoption_4_cicd_weak)
    medium = sum(1 for s in sessions if s.adoption_4_cicd_medium)
    strong = sum(1 for s in sessions if s.adoption_4_cicd_strong)

    total = len(sessions)
    return {
        "cicd_weak_rate": weak / total,
        "cicd_medium_rate": medium / total,
        "cicd_strong_rate": strong / total,
        "cicd_adoption_signal": strong / total,  # Only strong counts
    }
```

### Incumbent-Aware Adoption Model

```python
def aggregate_adoption_with_incumbent(sessions: list[SessionScore]) -> dict:
    """
    "We already use X" is NOT automatically a barrier.

    Incumbent status:
    - Has incumbent + satisfied → baseline, not barrier
    - Has incumbent + dissatisfied → real switching friction
    - No incumbent → greenfield adoption
    """
    has_incumbent = sum(1 for s in sessions if s.warning_2_has_incumbent)
    incumbent_satisfied = sum(
        1 for s in sessions
        if s.warning_2_has_incumbent and s.warning_2_incumbent_satisfied
    )
    incumbent_dissatisfied = has_incumbent - incumbent_satisfied
    no_incumbent = len(sessions) - has_incumbent

    # Switching friction: has incumbent but considering switch
    switching_friction = sum(
        1 for s in sessions
        if s.warning_2_has_incumbent and s.tct_override_behavior == "DEFER"
    )

    return {
        "incumbent_rate": has_incumbent / len(sessions),
        "incumbent_satisfied_rate": incumbent_satisfied / has_incumbent if has_incumbent else 0,
        "incumbent_dissatisfied_rate": incumbent_dissatisfied / has_incumbent if has_incumbent else 0,
        "switching_friction_rate": switching_friction / has_incumbent if has_incumbent else 0,
        "greenfield_rate": no_incumbent / len(sessions),
    }
```

## 3. Trust Calibration Score (v1.1)

### TCT-1 Conditional Scoring

```python
def compute_trust_calibration(sessions: list[SessionScore]) -> dict:
    """
    v1.1 TCT-1 scoring:
    - ConfigGuard = +2
    - Baseline = 0
    - Depends: classify based on dependency reason

    If "depends on" is solvable product gap → +1
    If "depends on" is fundamental doubt → 0
    """
    scores = []
    dependency_reasons = {
        "SOLVABLE_PRODUCT_GAP": [],
        "FUNDAMENTAL_DOUBT": [],
        "WORKFLOW_MISMATCH": [],
    }

    for s in sessions:
        if s.tct_baseline_trust == "ConfigGuard":
            scores.append(2)
        elif s.tct_baseline_trust == "Baseline":
            scores.append(0)
        else:  # Depends
            reason = s.tct_dependency_reason
            dependency_reasons[reason].append(s.session_id)
            if reason == "SOLVABLE_PRODUCT_GAP":
                scores.append(1)
            # FUNDAMENTAL_DOUBT and WORKFLOW_MISMATCH get 0

    total_trust = sum(scores)
    max_trust = len(sessions) * 2  # max 2 per session

    return {
        "trust_score": total_trust / max_trust,
        "trust_raw": total_trust,
        "dependency_reasons": dependency_reasons,
        "conditional_trust_rate": len(dependency_reasons["SOLVABLE_PRODUCT_GAP"]) / len(sessions),
        "fundamental_doubt_rate": len(dependency_reasons["FUNDAMENTAL_DOUBT"]) / len(sessions),
    }
```

def classify_behavior(s: SessionScore) -> str:
    """Classify user into behavioral pattern for analysis."""
    # Priority: Skeptic first (most distinct), then others
    if len(s.verbatim_skeptic_questions) >= 2:
        return "SKEPTIC"
    if s.warning_2_has_incumbent and s.tct_override_behavior == "DEFER":
        return "PRAGMATIST"
    if s.adoption_4_cicd_strong:
        return "OPERATOR"
    if s.tct_dependency_reason == "SOLVABLE_PRODUCT_GAP":
        return "AUDITOR"
    if s.h1_score >= 3 and s.adoption_2_explain_used:
        return "ANALYST"
    return "UNKNOWN"

### Adoption Tier Classification

```python
def classify_adoption_tier(s: SessionScore) -> str:
    """
    IMMEDIATE: Will adopt after trying
    CONSIDERING: Will adopt if conditions met
    WAITING: Product dependency gates adoption
    REJECTING: Actively opposes or prefers incumbent
    """
    # Strong adoption signals + follows ConfigGuard
    if s.adoption_signals >= 4 and s.tct_override_behavior == "FOLLOW":
        return "IMMEDIATE"

    # Adoption signals present but defers
    if s.adoption_signals >= 2 and s.tct_override_behavior == "DEFER":
        return "WAITING"

    # Conditionally interested
    if s.adoption_signals >= 1 and s.tct_override_behavior in ["FOLLOW", "ESCALATE"]:
        return "CONSIDERING"

    # Rejecting: Has incumbent + overrides or prefers baseline
    if s.warning_2_has_incumbent and s.tct_override_behavior == "OVERRIDE":
        return "REJECTING"
    if s.tct_baseline_trust == "Baseline":
        return "REJECTING"

    return "UNKNOWN"
```

## 5. Go/No-Go Decision Framework (v1.1)

### Decision Inputs

```python
@dataclass
class DecisionInputs:
    h1_pass_rate: float
    h2_actionable_rate: float
    h3_integrable_rate: float
    h4_preference_rate: float

    trust_calibration_score: float
    defer_rate: float
    adoption_probability: float

    top_adoption_tier: str
    top_blocker: str  # From DEFER condition analysis
```

### Decision Logic (v1.1)

```python
def compute_verdict(inputs: DecisionInputs) -> str:
    """
    v1.1 decision matrix:
    1. H1 must pass >= 80%
    2. 3/4 hypotheses must pass
    3. DEFER rate informs CONDITIONAL vs GO
    """

    hypotheses_passed = sum([
        inputs.h1_pass_rate >= 0.80,
        inputs.h2_actionable_rate >= 0.70,
        inputs.h3_integrable_rate >= 0.60,
        inputs.h4_preference_rate >= 0.50,
    ])

    # H1 is gate — if it fails, nothing else matters
    if inputs.h1_pass_rate < 0.80:
        return "NO-GO"

    # Need 3/4 to proceed
    if hypotheses_passed < 3:
        return "NO-GO"

    # 3/4 passed and H1 >= 80%
    if hypotheses_passed >= 3:
        if inputs.defer_rate > 0.4:
            return "CONDITIONAL"  # Product feature gaps
        if inputs.adoption_probability > 0.5:
            return "GO"
        else:
            return "CONDITIONAL"

    return "NO-GO"
```

2. **Is TCT-2 DEFER behavior correlated with H4 preference?**
3. **Do adoption signals cluster in specific user types?**
4. **What's the average time-to-first-understanding?**
5. **Which fix commands are modified vs applied directly?**

### Valid Conclusions from First Batch

```
Valid conclusions from first batch:
- Which hypothesis passes threshold
- Which user type needs most work
- What content is confusing (verbatim quotes)
- What adoption barriers exist (verbatim quotes)
- Whether test materials match real workflows
- DEFER conditions → product requirement backlog

### NOT Valid Conclusions from First Batch

```
NOT valid conclusions from first batch:
- "adoption_probability = 0.6" — Too few users to validate model

## 7. Per-User-Type Aggregation

```python
def aggregate_by_user_type(sessions: list[SessionScore]) -> dict:
    """
    Returns dict of ValidationResult per user type.
    Use to identify:
    - Which types adopt readily (amplifiers)
    - Which types need more evidence (risks)
    - Which types are decision blockers (power users)
    """
    USER_TYPES = [
        "Network Security Analyst",
        "DevOps/Platform Eng",
        "Security Auditor",
        "Platform Lead",
    ]

    results = {}
    for utype in USER_TYPES:
        type_sessions = [s for s in sessions if s.user_type == utype]
        if type_sessions:
            results[utype] = compute_verdict(type_sessions)
    return results
```

### Version History

| Version | Changes | Trigger |

| v1.0 | Initial design (all provisional) | First spec |

### Recalibration Triggers

After each user batch (n ≥ 6), evaluate:
1. **Metric drift** — Are scores clustering differently than expected?
2. **Missing signals** — What did users do that we didn't measure?
3. **Correlations** — Which signals predict actual adoption?
4. **Override patterns** — Is override behavior consistent?

## 9. Key Insight

**SAUS v1.0 revealed:** We were measuring perception but users were expressing system fit.

**v1.1 metrics now capture:**
- What users don't understand (H1x)
- What users are waiting for (DEFER + defer conditions)
- Which user types need which materials (B variants)
- CI/CD intent strength (not just presence)
- Incumbent status (not automatically a barrier)

## 10. Interpretation Layer Reference

**IMPORTANT:** The metrics system (v1.1) is a **frozen measurement layer**. It does NOT include adoption failure interpretation.

For post-session classification of adoption failures, see:
```
docs/superpowers/specs/validation/interpretation/adoption-failure-taxonomy.md
```

The taxonomy provides:
- F1–F7 failure mode classification
- failure_classification_confidence (0.0–1.0 per session)
- Behavioral signals → failure type mapping
- Temporal handling for F3 (Silent) time-dependency

**Critical:** Do not use taxonomy classification in GO/NO-GO decision. Use it as interpretive lens only.
