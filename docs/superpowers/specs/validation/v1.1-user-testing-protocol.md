## 1. Test Hypotheses

### H1: Output Understandability (Comprehension + Workflow Fit)

**Hypothesis:** Security engineers can understand CLI output without training.

**Sub-dimensions:**

| Sub-dimension | Tests | Success |
|---------------|-------|---------|
| H1a: What changed? | Identifies config change correctly | Pass if 4/4 |
| H1b: What does output describe? | Maps output to security concepts | Pass if 4/4 |
| H1c: What action is implied? | Identifies correct next action | Pass if 4/4 |
| **H1x: Unmet Questions** | Questions output doesn't answer (NEW) | Pass if ≤1 |

**H1x Scoring:**
```
0 questions → H1x pass
1 question  → H1x partial (count as signal, not failure)
>1 questions → H1x fail (legitimate gaps)
```

**NEW H1 Questions:**
```
Q1: "What do you understand this output to say?"
Q2: "What changed in this config?"
Q3: "How risky is this change on a scale of 1-10?"
Q4: "What would you do next?"
Q5: "What questions does this output NOT answer that you wish it did?"  ← NEW
```

**Scoring:**
- Q1-4: Correct answer = 1 point each
- Q5: No questions = 0, Legitimate questions = signal (not penalty)
- Total: 4/4 = full understanding, 2/4 = partial, <2 = failed

### H2: Actionability

**Hypothesis:** Engineers will act on `explain` output to fix issues.

**Test:** Give them Material B + explain output, ask:
- "Would you apply these fix commands?"
- "Would you need to modify them?"

**Success criteria:** 70% say "yes, I would apply or modify".

### H3: Workflow Integration

**Hypothesis:** Engineers will integrate ConfigGuard into CI/CD pipeline.

**Test:** Show them Material C + CI mode + exit codes, ask:
- "Would this fit in your deployment workflow?"
- "What would prevent adoption?"

**Success criteria:** 60% say "yes, with minor adjustments".

### H4: Competitive Differentiation

**Hypothesis:** ConfigGuard is preferred over manual audit / scripts.

**Test:** Compare ConfigGuard output vs. current method, ask:
- "Which would you use daily?"

**Success criteria:** >50% prefer ConfigGuard over current method.

## 3. Trust Calibration Tests (v1.1)

### TCT-1: Trust Calibration Test (P3 Fix)

**Hypothesis:** ConfigGuard earns trust vs. manual methods

```
[Show Material A: ConfigGuard diff output]
[Show baseline: Manual SSH + show commands interpretation]

Q1: "Which would you trust for a real security decision?"
A: ConfigGuard / Baseline / Depends

Q2: "Why?" [Record verbatim]

Q3: "What would need to be true for ConfigGuard to be your primary tool?"
[Record verbatim — this is tct_dependency_reason]
```

**Scoring (v1.1):**
```
ConfigGuard = +2 (trust signal)
Baseline = 0 (status quo bias)
Depends:
  → If dependency is solvable product gap (e.g., "control mapping") = +1
  → If dependency is fundamental doubt (e.g., "prove it's not giving false positives") = 0
```

**NEW field: `tct_dependency_reason`**
- Record what the "depends on" condition is
- Classify as: SOLVABLE_PRODUCT_GAP / FUNDAMENTAL_DOUBT / WORKFLOW_MISMATCH

### TCT-2: Override Test (P2 Fix — 4 States)

**Hypothesis:** Users with strong opinions will override ConfigGuard assessment

```
[Show Material A with ConfigGuard saying: Risk Delta +37 (MEDIUM)]

Q1: "What is YOUR personal risk assessment? Rate 1-10"
[Record rating — ask BEFORE revealing ConfigGuard rating]

Q2: "ConfigGuard says MEDIUM. You rated [X]. What would you do?"
A: Follow / Override / Escalate / Defer

[If Override]: "What would need to be true for you to follow ConfigGuard?"
[Record verbatim]

[If Defer]: "What would need to be true for you to make a decision?"
[Record verbatim — this is verbatim_defer_conditions]
```

**4 Response States (v1.1):**

| State | Definition | Score |
|-------|------------|-------|
| FOLLOW | Will follow ConfigGuard recommendation | +2 |
| OVERRIDE | Has stronger opinion, will override | 0 |
| ESCALATE | Needs more info before deciding | +1 |
| DEFER | Waiting for integration/features/evidence | +1 (conditional) |

**DEFER Definition:**
```
Not: "I don't trust this"
Not: "I don't understand this"
Not: "I need more information"

DEFER means: "I would decide, but product dependency gates my decision"
Examples:
  - "Need to see it integrate with our CMDB first"
  - "Waiting for Skybox integration before switching"
  - "Would adopt if they add asset classification"
```

**This is critical product signal:** DEFER tells us what's blocking adoption, not distrust.

### TCT-3: Fix Execution Test

**Hypothesis:** Fix recommendations are executable without modification

```
[Show Material B: explain output with fix commands]

Q1: "Can you apply these fix commands to your environment?"
A: Yes / With changes / No

Q2: "What would you need to change?"
[Record verbatim]

Q3: "How long would this take you?"
< 15 min = +2
15-30 min = +1
> 30 min = 0
```

## 5. Adoption Signals (v1.1 — P4 Fix)

### CI/CD Intent Strength

The question "Do you have CI/CD integration?" is NOT automatically an adoption signal.

```
Weak (not adoption signal):
  "Do you have a GitHub Action?" — just curious

Medium (weak adoption signal):
  "How does it integrate with CI?" — considering, not committed

Strong (real adoption signal):
  "How would I block PR on HIGH severity?" — concrete use case
  "Can I run this pre-commit?" — specific workflow question
```

**Capture fields:**
```
adoption_4_cicd_weak:  (bool) — "Do you have GitHub Action?"
adoption_4_cicd_medium: (bool) — "How does it integrate with CI?"
adoption_4_cicd_strong: (bool) — Concrete integration question
```

### Full Adoption Signal Set

| Signal | Definition | Strength |
|--------|------------|----------|
| adoption_1 | ttfu < 5 min (no help needed) | Strong |
| adoption_2 | explain command used voluntarily | Strong |
| adoption_3 | "This makes sense" unprompted | Strong |
| adoption_4_cicd_weak | Asks about CI/CD existence | Weak |
| adoption_4_cicd_medium | Asks about integration method | Medium |
| adoption_4_cicd_strong | Concrete integration use case | Strong |
| adoption_5 | Offered to share with colleagues | Strong |

## 6. Warning Signals (v1.1 — P6 Fix)

### Incumbent-Aware Model

**"We already use X" is NOT automatically a warning signal.**

It may mean:
1. User has established workflow (baseline, not resistance)
2. ConfigGuard needs to prove differentiation
3. Switching cost is real barrier

**When user says "we already use X":**

```
Step 1: Identify incumbent
  → Record: warning_2_incumbent_name = X

Step 2: Classify response type:
  - Satisfied incumbent: "Skybox works fine for us" → NOT a warning, baseline
  - Dissatisfied incumbent: "Skybox is painful but we're stuck" → real barrier
  - Conditional incumbent: "Depends if ConfigGuard is better" → switching friction

Step 3: Ask follow-up:
  "What would need to be true for you to switch?"
  [Record verbatim — verbatim_defer_conditions]
```

**Revised warning signal definitions:**

```
warning_1: Required explanation to understand output
warning_2_has_incumbent: Uses another tool (NOT automatically negative)
  → If incumbent satisfied: treat as baseline, not barrier
  → If incumbent dissatisfied: treat as real barrier
warning_3: Needs team check before adoption (may be organizational)
warning_4: Config change not worth action (legitimate workflow concern)
warning_5: Asked about pricing before trying (may be ROI evaluation)
```

## 7. Verbatim Capture System (P7)

**These fields capture the "why" behind scores:**

### verbatim_skeptic_questions
Questions skeptic users ask that indicate methodology质疑:
```
Examples:
- "How was this risk score calculated?"
- "What data trained this model?"
- "How do I verify this is correct?"
- "Can I see the raw diff?"
```

### verbatim_trust_killers
Phrases that indicate trust cannot be established without evidence:
```
Examples:
- "I've been burned by automation before"
- "We had a similar tool that gave false positives"
- "I need to see it work for 6 months first"
```

### verbatim_defer_conditions
What users are waiting for before they'll decide:
```
Examples:
- "Need to see integration with ServiceNow"
- "Would switch if asset classification was included"
- "We won't move without team consensus"
```

### verbatim_adoption_triggers
Unprompted phrases that indicate adoption likely:
```
Examples:
- "I'm going to show this to my team"
- "We could use this in our CI pipeline"
- "This would have caught the incident last month"
- "I want to try this on a real config"
```

## 10. Go/No-Go Decision (v1.1)

### Decision Matrix

```
H1 Pass ≥80%?
├─ NO → NO-GO (output not understood)
└─ YES → Continue

     3/4 Hypotheses Pass?
     ├─ NO → NO-GO
     └─ YES → Continue

          H1 ≥80% + Adoption Prob > 0.5?
          ├─ YES → GO
          └─ NO → CONDITIONAL GO
```

### DEFER Impact on Decision

**Important:** DEFER in TCT-2 does NOT count as adoption failure.

DEFER indicates product dependency, not product rejection.
- If >40% DEFER: Product has blocking feature gaps
- If >60% DEFER: Product is pre-adoption (not rejected, just early)

**Action for high DEFER rate:**
```
→ Not NO-GO
→ But v1.1 roadmap must address DEFER conditions
→ Track DEFER conditions as product requirements
```

## 11. Session Execution Guide

### Critical Timing: TCT-2 Override Test

```
WRONG (contaminated):
1. Show "ConfigGuard says MEDIUM"
2. Ask "What's YOUR rating?"

RIGHT (clean):
1. Ask "What's YOUR personal risk rating? 1-10"
2. THEN reveal "ConfigGuard says MEDIUM"
3. Ask "What would you do?"
```

### Critical Timing: Incumbent Detection

When user says "we already use X":

```
1. DON'T treat as warning signal automatically
2. ASK: "What do you like about it? What frustrates you?"
3. CLASSIFY: Satisfied / Dissatisfied / Conditional
4. THEN ASK: "What would need to be true to switch?"
```

### Material B Matching (Critical)

| User Type | Use Material | Why |
|-----------|-------------|-----|
| Network Security Analyst | B-standard | Standard security focus |
| DevOps/Platform Eng | B-operator | CI/CD integration focus |
| Security Auditor | B-auditor | Control mapping required |
| Platform Lead | B-standard | Multi-vendor overview |
| Skeptic profile | B-skeptic | Methodology challenge |

## 14. Key Insight

**SAUS v1.0 revealed:** We were measuring perception but users were expressing system fit.

**v1.1 fix:** Instruments now capture:
- What users don't understand (H1x)
- What users are waiting for (DEFER + defer conditions)
- Which user types need which materials (B variants)
- CI/CD intent strength (not just presence)
- Incumbent status (not automatically a barrier)
